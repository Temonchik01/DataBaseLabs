# Лабораторна робота №5: Нормалізація бази даних

## Цілі

- **Пошук надлишковості та аномалій:** виявлення потенційної надлишковості даних (наприклад, повторювані значення) або аномалій оновлення (проблеми вставки/оновлення/видалення) у поточній схемі.
- **Перелік функціональних залежностей:** визначте та перелічіть функціональні залежності (ФЗ) для кожної проблемної таблиці.
- **Перевірка нормальних форм:** оцініть поточну нормальну форму кожної таблиці (1NF, 2NF, 3NF) на основі її функціональних залежностей (ФЗ) та структури ключа.
- **Застосування нормалізації:** перетворення таблиць у вищі нормальні форми (до 3НФ) для усунення часткових та транзитивних залежностей.

## 1. Аналіз початкової схеми
В ході аналізу бази даних, розробленої в попередніх лабораторних роботах (система управління персонажами та інвентарем), було проведено перевірку таблиць на відповідність нормальним формам. 

Основними об'єктами аналізу стали таблиці:
*   `BaseCharacter` (Шаблони персонажів)
*   `Weapon` (Характеристики зброї)
*   `Item` (Предмети)
*   `Inventory` (Зв'язок персонажів та предметів)

## 2. Функціональні залежності (ФЗ)

Для кожної таблиці було визначено мінімальний набір функціональних залежностей:

### Таблиця `BaseCharacter`
*   **PK:** `id`
*   **ФЗ:** -> {name, max\_hp, max\_attack, max\_defence, max\_ammo, max\_speed\}
*   *Обґрунтування:* Кожен персонаж має унікальний набір характеристик, які залежать виключно від його ідентифікатора.

### Таблиця `Weapon`
*   **PK:** `id`
*   **ФЗ:** -> {name, damage, fire\_rate, ammo\_capacity, weight\}
*   *Обґрунтування:* Технічні параметри конкретної моделі зброї однозначно визначаються її ID.

### Таблиця `Inventory`
*   **PK:** `{character_id, item_id}` (складений ключ)
*   **ФЗ:** {character\_id, item\_id\} -> {quantity\}
*   *Обґрунтування:* Кількість предметів quantity залежить від того, який саме предмет item\_id належить конкретному персонажу character\_id.

## 3. Перевірка нормальних форм

### Перша нормальна форма (1NF)
*   **Вимога:** Всі атрибути атомарні, відсутні повторювані групи.
*   **Аналіз:** У всіх таблицях дані представлені в елементарному вигляді. Наприклад, у `BaseCharacter` характеристики винесені в окремі стовпці, а не зберігаються списком чи масивом.
*   **Висновок:** Схема відповідає **1NF**.

### Друга нормальна форма (2NF)
*   **Вимога:** Відповідність 1NF та відсутність часткових залежностей (неключові атрибути мають залежати від усього складеного ключа, а не від його частини).
*   **Аналіз:** 
    *   У таблицях з простим ключем (`BaseCharacter`, `Weapon`) часткова залежність неможлива. 
    *   У таблиці `Inventory` атрибут `quantity` залежить від повної комбінації `character_id` та `item_id`. Неможливо знати кількість, знаючи лише ID персонажа без предмета.
*   **Висновок:** Схема відповідає **2NF**.

### Третя нормальна форма (3NF)
*   **Вимога:** Відповідність 2NF та відсутність транзитивних залежностей (неключові атрибути не повинні залежати від інших неключових атрибутів).
*   **Аналіз:** У таблицях немає ланцюжків залежностей виду A->B->C. Наприклад, у `BaseCharacter` зміна імені (`name`) не тягне за собою автоматичну зміну швидкості (`max_speed`) згідно з логікою схеми. Всі характеристики є незалежними описами сутності.
*   **Висновок:** Схема відповідає **3NF**.

## 4. Результати та висновки щодо рефакторингу

Оскільки поточна архітектура бази даних була спроектована з урахуванням цілісності даних на етапі створення ER-діаграми, вона **вже перебуває у третій нормальній формі (3NF)**.

**Обґрунтування відсутності змін:**
1.  **Надлишковість:** Дані не дублюються. Кожен факт (наприклад, шкода конкретної зброї) зберігається лише в одному місці.
2.  **Аномалії оновлення:** При зміні характеристик предмета нам потрібно оновити лише один рядок у таблиці `Item`/`Weapon`, що автоматично відобразиться для всіх власників цього предмета.
3.  **Аномалії видалення:** Видалення гравця з бази не призводить до видалення загальної інформації про типи зброї або предметів, які існують у грі.

**Фінальний висновок:** Схема є оптимальною для поточних бізнес-вимог проекту. Оригінальні SQL-скрипти `CREATE TABLE` залишаються без змін, оскільки вони повністю забезпечують третю нормальну форму.
